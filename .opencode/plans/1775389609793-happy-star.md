# Table Normalization Plan (All Pages)

## Objective
Standardize all table experiences across `/master`, `/pengaturan`, and `/laporan` so they match current design system tokens/patterns, remove one-off implementations, and introduce a reusable industry-standard DataTable foundation with server-side-sort-ready contracts.

## Pre-Implementation Context Protocol
1. Run `/teach-impeccable` first (no existing impeccable context was found in repo).
2. Reconfirm existing design system sources before touching code:
   - `AGENTS.md`
   - `components.json`
   - `src/index.css`
   - `src/components/ui/table.tsx`
   - `src/components/ui/pagination-controls.tsx`
   - `src/components/ui/table-skeleton.tsx`

## Key Issues Found
- Table primitives exist, but page-level implementations duplicate loading/empty/actions patterns.
- Inconsistent action column conventions (`w-24 text-right` vs `w-[100px]` left-aligned).
- Repeated ad-hoc skeleton and empty-row logic across routes.
- Patient list uses raw nested pagination shape (`data.data`) and ignores pagination metadata.
- Two API pagination shapes in codebase (`PaginatedResponse` vs `PaginatedDataResponse`) reduce reuse.

## Recommended Architecture
Create a reusable feature-level table layer that composes current UI primitives and centralizes behavior.

### New Shared Files
- `src/components/data-table/types.ts`
  - `DataTableColumn<T>`
  - `DataTableSortState`
  - `DataTablePaginationState`
  - normalized table metadata types
- `src/components/data-table/data-table.tsx`
  - Generic table renderer using `@/components/ui/table`
  - Standard loading/empty states
  - Standard action column alignment/width conventions
  - Supports `comfortable` and `report` variants, sticky header, wrap policy
- `src/components/data-table/data-table-pagination.tsx`
  - Wrapper around `@/components/ui/pagination-controls`
  - Consistent footer + total rows + pending handling
- `src/components/data-table/data-table-toolbar.tsx`
  - Optional reusable search/filter/sort controls slot for list pages
- `src/components/data-table/index.ts`
  - Barrel exports

### API Normalization Files
- `src/services/adapters/pagination.ts`
  - Normalize both `PaginatedResponse<T>` and `PaginatedDataResponse<T>` into one frontend shape:
    - `items`
    - `meta: { currentPage, totalPages, perPage, totalItems, hasPrevPage, hasNextPage }`
- `src/services/types/query.ts`
  - Shared server-ready table query params:
    - `page`, `per_page`, `sort_by`, `sort_order`, plus feature-specific filters

## Patient Table Contract (Server-Sort Ready)
Update patient flow to consume normalized pagination and expose server-sort-ready params.

### Files to Update
- `src/services/patient.ts`
  - Extend `PatientSearchParams` with `sort_by`, `sort_order`
  - Keep backend-compatible key naming
- `src/hooks/use-patient.ts`
  - Return normalized list payload (avoid route-level `data?.data?.data` access)
- `src/routes/master/pasien.tsx`
  - Migrate to shared DataTable
  - Columns: `Name`, `BPJS`, `WA`, `Email`, `Actions`
  - Keep null-safe display (`-` fallback)
  - Add shared pagination controls from normalized metadata
  - Keep search debounce, reset page on search/per_page changes
  - Keep edit action in standardized action cell

## Route Migration Plan
Migrate by groups to reduce regressions and keep reviewable diffs.

### Phase 1 - Foundation
- Build `src/components/data-table/*` and pagination adapter.
- Keep visual parity with existing look (tokens/variants from design system).

### Phase 2 - `/master` routes
- Start with `src/routes/master/pasien.tsx` as reference migration.
- Then migrate:
  - `src/routes/master/users.tsx`
  - `src/routes/master/roles.tsx`
  - `src/routes/master/poli.tsx`
- Unify action cells, empty states, loading states, row spacing.

### Phase 3 - `/pengaturan` routes
- Migrate pages using tables to shared DataTable shell:
  - `src/routes/pengaturan/konfigurasi-sistem.tsx`
  - `src/routes/pengaturan/konfigurasi-whatsapp.tsx`
  - `src/routes/pengaturan/faq.tsx`
  - `src/routes/pengaturan/konfigurasi-pengingat.tsx`
  - `src/routes/pengaturan/jadwal-kontrol.tsx`
  - `src/routes/pengaturan/template-pesan.tsx`
- Standardize pagination placement and controls where applicable.

### Phase 4 - `/laporan` routes
- Migrate report tables in `src/routes/laporan/index.tsx` to shared DataTable with `variant="report"`.
- Preserve report semantics while normalizing header/body/action/empty/loading patterns.

### Phase 5 - Cleanup
- Remove orphaned duplicated table fragments/skeleton implementations in route files.
- Ensure all migrated pages rely on shared DataTable APIs only.

## UX/Design Normalization Rules to Enforce
- Typography: keep table header/body text sizing from existing `Table` variants only.
- Color/theme: use semantic tokens from `src/index.css`; remove one-off colors.
- Spacing/layout: use consistent cell padding through variant system; no per-page random widths unless justified.
- Components: prefer design system primitives and shared DataTable wrappers.
- Interaction/motion: consistent hover/focus states; no custom divergent interaction patterns.
- Responsive: preserve horizontal scroll container behavior and avoid clipped actions.
- Accessibility: focus-visible states, icon buttons with labels, sortable header semantics (`aria-sort`) when enabled.

## Risks and Mitigations
- Backend sort params mismatch
  - Mitigation: centralize param mapping in service layer; keep optional sort params.
- Visual drift during migration
  - Mitigation: migrate route-by-route with parity-first approach.
- Pagination metadata edge cases
  - Mitigation: robust adapter defaults and null-safe handling.
- Over-abstraction risk
  - Mitigation: keep DataTable APIs minimal and composable; avoid feature-specific coupling.

## Verification
Run after each migration phase and again at end:
- `bun run lint`
- `bun run build`
- `bun dev`

Manual checks (all migrated pages):
- Loading state uses consistent skeleton style.
- Empty state uses consistent row height and message presentation.
- Action column alignment/spacing is consistent and keyboard accessible.
- Pagination controls behave correctly (first/prev/next/last, per-page changes, pending state).
- Search + pagination interaction is stable (search resets to page 1).
- Patient columns render exactly: Name/BPJS/WA/Email/Actions with null-safe display.
- Report tables retain readability and consistency in `report` variant.
- Mobile/desktop/ultra-wide checks: no overflow clipping beyond intended horizontal scroll.

# Incremental Plan: Fix `useDoctorData` Runtime Export Error

## Problem
Runtime error on dev server:
`The requested module '/src/hooks/index.ts?...' does not provide an export named 'useDoctorData'`

## Root Cause (Most Likely)
Barrel self-import cycle in hooks layer:
- `src/hooks/index.ts` re-exports `./use-doctor-data`
- `src/hooks/use-doctor-data.ts` imports `useUserList` from `@/hooks` (the same barrel)

This can cause ESM export resolution/HMR graph issues where runtime cannot resolve `useDoctorData` reliably.

## Recommended Fix

### 1) Break cycle at source
- Update `src/hooks/use-doctor-data.ts`:
  - Replace `import { useUserList } from "@/hooks"`
  - With direct module import: `import { useUserList } from "./use-user"` (or `@/hooks/use-user`)

### 2) Keep barrel export for consumers
- Keep `src/hooks/index.ts` exporting `use-doctor-data` so external modules can still use `@/hooks`.

### 3) Optional hardening at usage point (only if needed)
- If runtime issue persists in dev after step 1, change `src/routes/jadwal/index.tsx` to import:
  - `useDoctorData` from `@/hooks/use-doctor-data`
  - keep other hooks from `@/hooks`

### 4) Add guardrail to prevent recurrence
- In ESLint config, add restricted import rule for files inside `src/hooks/**/*`:
  - forbid importing from `@/hooks` and `@/hooks/index` inside hook modules
  - enforce direct intra-folder imports for hook-to-hook usage

## Files To Modify
- `src/hooks/use-doctor-data.ts` (required)
- `src/routes/jadwal/index.tsx` (optional fallback)
- `eslint.config.js` (recommended guardrail)

## Verification

### Static checks
- Run `bun run lint`
- Run `bun run build`

### Runtime checks
- Run `bun dev`
- Open `/jadwal`
- Confirm no browser console/runtime error for missing export `useDoctorData`

### Regression check
- Search for barrel self-imports in hooks and ensure none remain:
  - `mgrep`: "inside src/hooks files importing from @/hooks barrel"

## User-Confirmed Direction
- Personality lane: **Clinical Signage**
- Scope: **Poly cards only** (not whole page)
- Motion: **Subtle only**
- Brand tone: **keep clinical, calm, efficient**

# Incremental Plan: Global Confirmation Dialog Normalization

## User-Confirmed Scope
- Confirmation required for: **data-changing actions only**
  - include create/update/delete/restore/status transitions
  - exclude search/filter/pagination/tab/navigation/export/non-mutating UI actions
- Form submit confirmations: **only critical forms** (not all high-frequency forms)
- Copy style: **detailed** by default (title + description + entity + impact + recovery when relevant)

## Objective
Normalize all mutating action buttons to use a confirmation step first, aligned with existing design system primitives (`ConfirmDialog` + `AlertDialog`) and consistent UX language across modules.

## Design System Sources (Authoritative)
- `src/components/ui/confirm-dialog.tsx` (app-level confirmation contract)
- `src/components/ui/alert-dialog.tsx` (primitive behavior and structure)
- `AGENTS.md` (project conventions)
- `.impeccable.md` (tone guidance: clinical, calm, efficient)

## Current Gaps Found
- Confirmation exists in many routes but inconsistent depth/copy/variant usage.
- Some mutating flows still have direct action without confirmation.
- Delete/terminal actions are not consistently marked `destructive`.
- Content quality varies; some dialogs lack entity/impact/recovery context.

## Normalization Matrix (Target Behavior)

### 1) Destructive actions
Examples: delete, hard terminal/no-show actions with operational consequence.
- `variant="destructive"`
- Must include: `entityName`, `impactItems`, `recoveryHint`
- Confirm text follows action verb: `Hapus`, `Tandai No Show`, etc.

### 2) Mutating but non-destructive
Examples: restore, state progression, save critical settings.
- `variant="default"`
- Must include: clear title/description
- Should include: `entityName`
- Optional: `impactItems` when outcome affects workflow visibility

### 3) Critical forms (save/update/create)
Only for forms with high operational/system impact.
- Confirmation required before submit
- `variant="default"`
- Include concise impact bullets (1–3)

## Critical Forms (Initial Target)
- `src/routes/pengaturan/konfigurasi-sistem.tsx`
- `src/routes/pengaturan/konfigurasi-whatsapp.tsx`
- `src/routes/pengaturan/konfigurasi-pengingat.tsx`
- `src/routes/pengaturan/template-pesan.tsx` (for impactful template changes)
- `src/routes/administrasi/antrean.tsx` and `src/routes/dokter/antrean.tsx` for status-changing submit paths

## Rollout Plan

### Phase 1 — Standardize confirmation payload shape
- Ensure every existing `ConfirmDialog` call follows matrix above.
- Normalize prop completeness and consistent button labels.

### Phase 2 — Add missing confirmations in mutating routes
- Priority P0 (operational-risk):
  - `src/routes/perawat-asisten/antrean.tsx` (no-show/call transitions)
- Priority P1 (master/settings + schedule):
  - `src/routes/master/pasien.tsx`
  - `src/routes/master/users.tsx`
  - `src/routes/master/roles.tsx`
  - `src/routes/master/poli.tsx`
  - `src/routes/jadwal/index.tsx`

  - `src/routes/pengaturan/jadwal-kontrol.tsx`
  - `src/routes/pengaturan/template-pesan.tsx`

### Phase 3 — Queue flow consistency

  - `src/routes/administrasi/antrean.tsx`

- Add `pendingAction` state object + `confirmOpen` state.
- Replace direct mutation button handlers with `requestConfirm(actionMeta)`.
- Mutation executes only in `onConfirm` callback.
- Ensure pending state prevents double-submit.
